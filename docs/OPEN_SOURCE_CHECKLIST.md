# Open-Source Readiness Checklist

This repository is close to a typical academic artifact release, but it still
needs a few policy and packaging decisions before public release.

## Already Improved

- Root README explains the project, layout, environment, build flow, generated
  files, and citation.
- `CITATION.cff` lets GitHub and citation tools expose the paper metadata.
- `CONTRIBUTING.md` documents the expected contribution and issue-reporting
  workflow.
- `.gitignore` prevents new build/profiling artifacts from being committed.

## Recommended Before Publishing

- Choose and add a license. Common choices are MIT, BSD-3-Clause, Apache-2.0,
  or GPL, but the right choice depends on your institution and third-party code.
- Audit every imported benchmark under `include/` for license compatibility and
  attribution requirements.
- Decide whether checked-in experiment artifacts under `IPC/`, `metrics/`,
  `assem/`, and `omnitrace-*_output/` should stay in git, move to a GitHub
  Release/Zenodo artifact, or be regenerated by scripts.
- Remove checked-in CMake-generated files under `pass/CMakeFiles/`,
  `pass/Makefile`, and `pass/cmake_install.cmake` if they are not intentionally
  part of the artifact.
- Add an environment manifest, such as a Dockerfile or `environment.yml`, so
  readers can reproduce the ROCm/Python setup.
- Add a small smoke-test command that is known to complete quickly on a supported
  AMD GPU.
- Document the meaning and accepted values of `INJECT_BIT`.
- Document which benchmarks need `SOURCE_CPP=ON`.
- If the public repository will accept issues, add issue templates for build
  failures and reproduction questions.

## Optional Polish

- Move saved experiment artifacts to `artifacts/` or release assets.
- Add tables mapping paper figures/tables to scripts and output files.
- Add a `docs/reproduce.md` with exact commands for the paper's main results.
- Add CI checks for formatting and documentation links, even if GPU builds are
  run manually.
